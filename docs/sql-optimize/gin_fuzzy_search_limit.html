gin_fuzzy_search_limit 实测：默认 0 的 GUC，为何能让 GIN 索引静默丢行

2026-07-27 SQL优化 gin_fuzzy_search_limit GIN jsonb 数组包含 pg_trgm 查询正确性
✅ 已验证版 · PG 16.11 + 16.14 双版本实跑

一句话总结

gin_fuzzy_search_limit 默认 0，含义是"不限制 = 精确搜索"。一旦把它设成非 0 值，PostgreSQL 会对 GIN 索引扫描启用"模糊搜索"：扫描只返回 posting list 的随机子集，且数量只是近似；同一个 SELECT 跑两次可能返回不同行。我在 PG 16.11 与 16.14 上用 jsonb、数组、pg_trgm 三类 GIN 索引实跑验证，count(*) 从正确的 5000 塌到 80~110，且两次执行结果不一致。这个参数平时看不见，但谁手贱设了非 0，生产查询就可能静默返回错误结果——这是最危险的失败模式：不是报错，是返错还一声不吭。

一、参数层：默认 0，双版本一致

在 16.11 与 16.14 上分别 SHOW，结果完全相同：

(1 row)
  • 默认值 0：不限制，GIN 扫描返回全部匹配行（精确）。
  • context = user：可在会话 / 角色 / 库级 SET，无需重启。
  • 两版本一致：16.11 与 16.14 的默认值、上下文、分类完全相同。

也正因它是 user 级，任何会话都能悄悄打开——所以"谁动了它"很难从配置文件里反查，只能从异常结果倒推。

四、机制：为什么会丢行？

GIN 索引对高频键维护一个 posting list（命中行指针列表）。当某个键的 posting list 很大时，gin_fuzzy_search_limit 非 0 会让扫描只取前 N 个（近似）指针就不再继续，从而"以正确性换速度"。三个要点：

  • 触发条件看 posting list 大小，不看操作符：jsonb ?、数组 @>、pg_trgm 的 LIKE（gin_trgm_ops 索引）机制相同；只有当某键匹配量足够大、posting list 超过阈值，模糊才生效。这也解释了为什么小表测不出问题——表越大、匹配越密，坑越深。
  • 返回的是随机子集，不是"前 N 行"：所以同一查询两次执行，取的子集不同 → 行数不同、内容也不同。
  • count(*) 也中招：聚合统计同样基于这个残缺子集，于是"总数"也是错的。这比漏几行更毒——它让你的监控、对账、分页都建立在错误数字上，却没有任何报错提醒。

五、实战建议

  1. 生产保持默认 0：除非你明确知道自己在做"近似去重 / 采样"且能接受丢行，否则永远别动它。
  2. 排查线索：若某 GIN 查询（尤其全文检索、jsonb 路径、模糊 LIKE）结果忽多忽少、count 与明细对不上，先查 SELECT current_setting('gin_fuzzy_search_limit') 是不是被会话 / 角色 / 库级改过。
  3. 它不是诊断探针：与 enable_* 系列不同，设非 0 是"真的丢数据"，不是"换执行计划"。把它当性能开关用是危险误解。
  4. 双版本无差异：16.11 与 16.14 行为完全一致，升级不会自动改变这个坑——但也不会自动帮你避开。
